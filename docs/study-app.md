# Existing app audit

Audited on 2026-10-13 before implementation, against the starting app at `4c84fec` in `feat/app-zilion-0.3`. Read every source file under `src/`, including the complete 6,199-line main page; README, CLAUDE.md, package and Playwright configuration. Line references in this document describe that starting revision. This study supports `APP_PLAN.md`; it does not itself authorize changes to the paper or another checkout.

## Current architecture and behavior

The app is a Svelte 5 application with runes already used inside its main component. The architectural problem is ownership, not a Svelte 4 migration: about 1,645 lines of model/orchestration, 2,600 lines of UI/help, and 1,940 lines of CSS share one file. Only the Mermaid wrapper is extracted. SSR is explicitly disabled and the site prerenders statically (`src/routes/+layout.ts`).

The production engine imports the raw `Z80_CORE_WGSL` string from Zilion 0.2 and wraps it in app-owned shader code. It does not use the engine or world API. `GPUEngine` owns device, shader compilation, buffers, pair generation, execution, mutation, statistics, rendering, and camera navigation. `shaders.ts` generates separate square/hex simulation and rendering variants. The Z80 is initialized fresh for every pair with zeroed primary and shadow registers, PC 0 and SP 65535; code/data address by modulo pair length. Both resulting tapes are written back.

The 20,000-cell target grid is calculated from the initial viewport, with widths and heights bounded 40–400; UI fields advertise 50–500. Square cells hold 16 bytes, hex cells 19, packed into 4 and 5 uint32 words respectively. Pair candidates are randomly generated on GPU, and atomics claim disjoint cells. Square borders reflect an outwards direction inwards. Hex borders clamp coordinates and may produce a self-pair which is skipped. Mutations are random byte replacement events across valid bytes, with event count `floor(requestedPairCount / 2^noiseExp)` per batch. They are not bit flips or a per-byte Bernoulli probability.

### Other source modules

- `z80-opcodes.ts` contains a structured vocabulary of 768 base/CB/ED table entries, length and memory-write metadata, semantic families, pattern matching and bit-mask packing. This is stronger than the disassembler and should inform the Z80 ablation UI. Prefixes/undefined ED holes cannot be directly suppressed; DD/FD follows base; DDCB/FDCB follows CB. This is a policy decision that belongs in a manifest.
- `z80-disasm.ts` handles base and CB instructions and a subset of ED. DD/FD display as one-byte `DD ..`/`FD ..`; indexed instructions, displacement and DDCB forms are not actually decoded. ED loads consume operand length but do not format actual operands; missing operands may be displayed as zero. Static disassembly is a hypothesis, not an execution trace.
- `sim/z80.ts` is an old, separate CPU implementation used only by the uncalled `traceCell` helper. Its DD/FD paths explicitly treat IX/IY as HL, block I/O is a no-op, and refresh handling differs from the shipping Zilion core. The comments claiming it matches the GPU are stale. Never use this implementation for new culture/self-copy or scientific trace measurements.
- `sim/prng.ts` provides SplitMix64 with private state and no snapshot/restore API. `sim/soup.ts` extracts word-padded tapes and has an unused CPU trace renderer. `colormap.ts` holds four constructors, but only rainbow/ocean/thermal are selectable. The palette is Z80-specific and colors raw values, not actual executed opcodes.
- `checkpoint.ts` serializes PNG-tail payloads but trusts parsed JSON as a TypeScript type. `presets.ts` is a practical local-persistence utility, but setting values are `unknown` and validation is shallow (`values: null` passes the object test).
- `/demo` and `/demo/playwright` are scaffold pages. The only Playwright test asserts a visible demo `h1`; it does not load the app. `src/app.html` contains old Z80-only metadata and a throughput claim. The favicon is a terracotta ladybird, unrelated to the paper's proposed visual vocabulary.

## What works and the baseline run

The coordinator installed dependencies, ran the app locally at `http://localhost:5174`, and paused the baseline after approximately 45 seconds of GPU activity. Reported nominal throughput was around 500M instruction slots/s in that local run. Screenshots are in `docs/screenshots/baseline*.png`. Baseline `npm run check` returned zero errors and 20 accessibility warnings. This is one machine/browser observation, not a general performance benchmark.

The official Svelte MCP autofixer was also run against the complete baseline page. It reported the same 20 accessibility issues plus seven unkeyed each blocks, and suggested reviewing state assignments inside initialization effects and `bind:this`. Those findings are recorded here; no source was changed during the study phase. The planned component/state split resolves the ownership problem rather than merely hiding the diagnostics.

The byte lattice is the app's memorable element: richly textured at full extent and useful at close zoom. GPU-resident execution avoids per-step bulk CPU transfers. The distinction between live parameter edits and reseeding is already carefully considered in the preset schema. The opcode table makes ablation inspectable rather than a hidden shader edit. Square/hex packing shares code with the differential harness. Readbacks have pending-map guards, preventing an overlapping `mapAsync` exception. The `.acell` image-plus-state format is clever and worth keeping as an import bridge.

## Findings with evidence

### Scientific validity and reproducibility

1. **A seed is insufficient to specify the run.** Initial width/height depend on `window.innerWidth/innerHeight` (`+page.svelte:322`); pair claims depend on GPU scheduling (`shaders.ts:228`); mutation invocations use non-atomic read-modify-write on packed words (`shaders.ts:337`). Two mutations affecting different bytes of one uint32 can lose an update. Compat 0.2 should preserve core semantics, but exact prior soup trajectories cannot honestly be promised across GPU schedules. New research mode should use a deterministic schedule and explicit manifest/world.
2. **Checkpoint exact-resume claim is false.** Metadata saves a batch number but load never restores it or the private SplitMix64 state (`+page.svelte:953–997`, `checkpoint.ts:7–19`). It changes engine steps/pairs without updating `z80Steps`/`pairCount` control variables. Save calls `readSoupData` without pausing; when another read is pending the engine returns an empty array (`engine.ts:699`), which can serialize an empty checkpoint. PNG capture and soup capture are not one atomic snapshot. Imports have no version/range/buffer-size validation or surfaced error.
3. **Hex frequency normalization is wrong.** `TOTAL_BYTES` counts padded 20 bytes per cell (`+page.svelte:110`), but `count_bytes` explicitly excludes padding (`shaders.ts:345–359`). Fractions sum to 19/20, not one.
4. **“ops/s” is a budget estimate.** Credited operations are requested pairs × max steps (`engine.ts:597`), including inactive collisions and halted executions. Completed GPU queue work is used for timing, which is good, but the displayed count is not actual decoded instructions and README/meta claims should not call it measured CPU operations.
5. **“Species” means hash groups, not replication or lineage.** Full-tape identity is reduced to a 32-bit FNV hash; collisions are not checked. Richness threshold is `count >= max(1, floor(N*.001))`, while help claims `p > .1%`. A dominant hash does not certify autonomous copying. Use “tape types” and exact byte identity for this scale, and a separate empirical culture assay.
6. **Statistics do not describe a common snapshot.** Hashes are awaited first, then a separate soup readback gives exemplars while execution continues. A hash may be paired with bytes from a later state. If another soup read is pending, exemplars are empty.
7. **Content overstates science.** Headings “Why Life Emerges” and “Why POP HL & EX (SP),HL Win” assert a universal progression. The chart is presented as a phase transition without measurement; analysis suggests ablation can produce error correction/division of labor without evidence (`+page.svelte:3502`, `4072`, `4204`). Replace with the paper's particular conditions and limits. “No fitness function” does not imply “no selection pressure.” Mutation descriptions interchange flips and replacements and assert higher mutation means faster evolution (`2625`).

### Performance and failure handling

1. **Pointer movement reads the entire soup.** Every valid mouse move requests a refresh; the animation loop calls `readSoupData` (`+page.svelte:713`), which copies all tape bytes to a staging buffer (`engine.ts:697`). A tiny selected-cell readback or a shared sampled snapshot would remove unnecessary work. Tooltip refresh timers are cleared on pointer leave but not in the component teardown.
2. **No queue backpressure.** Eight batches are submitted every animation frame whether prior GPU work completed; each step also registers an `onSubmittedWorkDone` promise. Rendering continues every frame when paused. Add one in-flight chunk, cancellation token, visibility suspension and an explicit burst limit.
3. **Lifecycle races.** The asynchronous `eng.init().then` can set state/start a loop after teardown. Init rejection is not caught, device loss is not handled, and readbacks may finish against destroyed/recreated buffers. The reset/grid handlers duplicate large history-clearing blocks and lack generation tokens.
4. **Measurement histories depend on presentation.** Byte history records only while chart visible; species/diversity update only on those tabs; sample spacing is every 15 animation frames (`+page.svelte:400`, `433`, `528`). There is no real step/time coordinate. “Ring” buffers shift 299 array references per sample. Species identity tracking stops accepting new hashes after 20 and draws only the first 10 (`561`), so later dominant types can be absent from the trend.
5. **Synchronous compilation is repeated.** `changeGridConfig` destroys/recreates all buffers and pipelines, including unchanged ISA pipelines. Separate world recompilation from grid resize and rely on the 0.3 engine cache. Render shader hex geometry is relatively expensive, recomputing neighbor Voronoi distances and averaging per pixel; retain as a showcase mode before optimizing with benchmarks.
6. **Failures are silent.** Statistics catches discard exceptions, invalid checkpoint data quietly returns, and the UI can continue displaying stale results. Surface a concise status and preserve last-good state. Validate before altering the active world.
7. **Runtime external request.** The main head loads KaTeX CSS from jsDelivr (`+page.svelte:1675`). Bundle local CSS or replace simple formulas with semantic text; no CDN request is necessary. Mermaid loads a substantial renderer for a two-node static diagram.

### UX, design and accessibility

1. **No first-read orientation.** A user lands in an already running, full-screen texture with icon-only chrome and no visible app identity or statement of the experiment. The desktop settings are only 220px wide, most labels 10px, chart tile labels 8.5px. The lattice should remain dominant, with a concise hypothesis, selected experiment and explicit run status around it.
2. **Controls blur experiment and appearance.** Presets mix scientific settings with color/brightness. Changing only ablation is silently live; selecting a paper experiment should explicitly start a fresh configured trial, with a separate “apply intervention” action if live manipulation is desired.
3. **Charts lack axes, units and accessible summaries.** Byte curves use `log2(256*p+1)` with a shared moving maximum; species uses `log2(100*p+1)`; diversity each gets its own maximum. None display these transformations. Prefer fixed [0,1] fractions for zero/share, entropy in nats with step labels, numerical summaries and CSV.
4. **Keyboard focus is explicitly removed.** `button:focus, button:focus-visible { outline:none }` (`+page.svelte:4273`). Inputs remove outlines; chart/species `div role=button tabindex=0` lacks keyboard activation (`1958`, `2038`). Canvas has no accessible name, fallback description or keyboard cell navigation.
5. **Dialogs are incomplete.** `role=dialog` lacks accessible names, `aria-modal`, initial focus, focus containment and restoration; Escape only runs when target is `document.body`, so focused dialog controls prevent dismissal. Native `<dialog>` with close handling is a better foundation.
6. **Zoom is disabled at the document level.** `app.html` sets `maximum-scale=1,user-scalable=no`. Page-wide hidden overflow and tiny font sizes compound this. Mobile shifts the info widget to top-left and toolbar to bottom, but overlapping settings still obscure the soup. Preserve pinch-to-zoom within the viewport while allowing browser page zoom and readable document scrolling.
7. **Several hit targets are undersized.** Settings info buttons are 14×14, close buttons 22×22, presets 18px high; touch sliders become larger but most actions do not. Use 40–44px interactive minimums for primary mobile actions.
8. **Color is overloaded.** Raw-byte palette implies Z80 opcode meaning even for operand bytes and other ISAs. Chart type IDs use average color (which can collide), and status distinctions are color-only. The new paper palette should reserve teal, vermilion and purple for known scientific categories, add labels/patterns and leave the general soup neutral unless inspecting byte identity.

## Proposed module contracts

Use a per-page `createSession()`/`SimulationSession` instance rather than module-global mutable state. Large typed arrays and engine handles remain plain fields or `$state.raw`; expose small reactive view state with `$state`, and computed labels/validation with `$derived`. Effects synchronize external rendering or lifecycle only. Explicit methods apply user actions, avoiding effects that chase multiple form changes and reset repeatedly. Official Svelte MCP documentation for `$state`, `$derived`, `$effect`, `$props`, `.svelte.ts` and context was read during this audit.

| `session.svelte.ts`              | Authoritative validated `ExperimentConfig`; machine/world identity; status, batch/interaction count; `initialize`, `run`, `pause`, `step`, `reset`, `applyPreset`, `dispose`; single in-flight chunk and generation token; no DOM |
| `engine.ts` or engine adapter    | `WorldSpec` + machine selection + initial memory/state → resident execution and explicit `Snapshot`; actual step/write/halt/fetch metrics; manifest; cancellation/disposal; never imports Svelte                                  |

| `ExperimentPanel.svelte`         | Config draft/preset catalogue + callbacks; shows parameter source and whether a change resets; machine/compat, budget, register setup, geometry, chemistry, ablation; group advanced details progressively                        |

## Safe first-refactor boundary

A new research desk is justified: desktop header, narrow experiment panel, dominant central lattice, right inspector and bottom labelled measurements; mobile uses normal scrolling with the lattice first and accessible sections. Every parameter must be discoverable and sourceable. White/charcoal paper chrome should frame the dark lattice without copying the old generic warm accent.

Retaining the full old page at a clearly marked **Legacy Z80 instrument** route is a defensible migration bridge. It preserves square/hex appearance controls, old local presets, floating inspection, keyboard controls and `.acell` support while the new engine/state boundaries settle. Freeze its CPU core to compat 0.2; do not run both engines simultaneously. Document that legacy scheduler nondeterminism and checkpoint limits remain. A route alone is not feature parity: the plan must name which capabilities are available only there. New default research mode must include primary run/pause/step/reset, source-linked presets, three ISAs, a real inspector, truthful initial measurements, About/Guide and import/export. It should label smaller browser workloads as demonstrations rather than replications of the full paper cohorts.

## Test priorities

- CPU-only schema tests: bounds, all preset definitions, tape lengths/rings/stack aliases, suppression counts, per-ISA decode representative instructions including truncated/prefixed sequences, measurement normalization and zero/diversity extremes.
- Engine fixture checks: frozen compat 0.2 outputs; corrected Z80/6502/8086 world outputs; exact manifest identity; one-shot versus chunks; fetch versus start semantics; deterministic checkpoint continuation; no-write ablation, lethal probability 0/1, register initialization.
- Playwright: real app loading; every preset applies and completes a small burst; ISA switch updates world/disassembly; keyboard/pointer inspector; selected-tape culture; About and Guide; export/import; mobile viewport and no horizontal overflow; no external requests; no console errors.
- Run required check/lint/build once implementation stabilizes, then scoped checks after fixes. Save desktop/mobile screenshots and critique text hierarchy, lattice dominance, legibility and working controls. Enforce GPU bursts ≤60 seconds, preferably 1–3 iterations for smoke tests.
